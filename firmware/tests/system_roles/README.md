# Whole-system tests with the real roles

Scenario tests that run the real sensor, siren and gateway roles together on one `Simulation` with the `TestHub`: M1a's "done when" with the real roles, and many sensors on one gateway (design section 8, "System tests").

Every `.cpp` here goes into `hsn_system_tests`, which links all three role libraries, `hsn_host` and `hsn_test_support` (include `sim_support.hpp` for the bench helpers), and is compiled without RTTI. The executable exists only once this folder has a `.cpp` file. Tests with the scripted devices instead of the roles go in `tests/system/`; tests of one role go in `tests/roles/<role>/`.

`system_site.hpp` builds a site (a `SystemSite`: the simulation, the test hub in gateway link mode, and `gateway()`, `sensor()`, `siren()` adding the real roles) and holds the questions the scenarios ask of the timeline and the hub. The day-long load cases are in the doctest test suite `long`; `hsn_system_tests -tse=long` leaves them out, `-ts=long --duration=true` runs only them and prints how long each took. Tests marked `BLOCKED:` are skipped: each is the test that should pass, with the evidence of what stops it.

The same scenarios run against the real hub in lockstep (hub-design.md section 11): `hsn_system_lockstep_tests` compiles section 11's system tests and M2's two (`group_sirens`, `schedule_arm`: groups, modes and schedules are the real hub's alone, so their files are empty outside `HSN_LOCKSTEP`) (`chain`, `restarts`, `lost_path`, `two_gateways`, `sirens`, `interference`, `heartbeat_reply`, `load`, `site_move`, and `../lockstep/real_hub_test.cpp`: a hub restart during a countdown, a gateway's session replaced and its old link closed by the hub) with `HSN_LOCKSTEP`, which makes `SiteHub` a `RemoteHub` instead of a `TestHub`; `hsn_lockstep_scripted_tests` does the same for `../system/armed_door_test.cpp` and `../host/test_hub_gateway_test.cpp` (`sim_support.hpp`'s `Site`). The text of each case is the same. They are the CTest group labelled `lockstep`, built only where Bun and the hub's sources are found, with the system tests run a second time with the hub taking 30 ms to send (`HSN_HUB_DELAY_MS`); `bun run check:firmware:lockstep` at the root runs the group alone.

On the real hub each board is provisioned over USB first: one more restart (`kProvisioningResets`), two more flash writes (`provisioning_flash_writes`), and setup messages on its USB link (`is_packet` tells them apart). A case is marked, with its reason: `HSN_FAILS_ON_REAL_HUB(why)` where the real hub, or the scripted device it is run with, is known to be wrong (there it must fail, so a fix shows); `HSN_NOT_ON_REAL_HUB(why)` where the case does not apply (a site of two data rates); `HSN_BLOCKED_ON_REAL_HUB(why)` while a hub fault stops it.
