# Protocol test vectors

Test cases for the device protocol, version 1 ([docs/protocol.md](../../../docs/protocol.md)). The TypeScript package and the C++ firmware both check every case on every build. The files are generated by `bun run vectors` in `packages/protocol` from fixed keys and values, with no randomness and no timestamps. A test fails if a committed file differs from what the generator writes, so do not edit them by hand.

## Conventions

- **Bytes** are lowercase hex strings with no separators. An empty string means zero bytes.
- **Integers** are JSON numbers. All fit an unsigned or signed 32-bit integer, so they are exact in any JSON reader that uses doubles.
- **Booleans** are JSON `true` or `false`.
- **Text** (log text only) is a JSON string. On the wire it is UTF-8; its byte length, not its character count, is what the limit applies to. Invalid UTF-8 never makes a packet invalid: it decodes with U+FFFD replacement characters, as WHATWG's UTF-8 decoder produces them (one per maximal invalid subsequence).
- **Enumerated values** (role, button action, siren action, state, reason, when, priority, result, interference event, site channel, data rate, provision result) are integers and may hold values version 1 does not list; such a packet is still valid and the value passes through unchanged (section 3). Each kind has at least one case whose name contains "unlisted".
- **Unused flag bits** are written as zero and ignored when read. Each flags byte that has unused bits (reply, siren report, gateway status) has a decode-only case with them set, whose name contains "unused flag bit". The sensor status flags byte has none: all eight bits are named, so it has no such case.
- **Names** are camelCase.
- **Directions** are numbers: `0` to the hub, `1` from the hub. This is both the header's bit 3 and the nonce's direction byte.
- **Errors** are the strings below. A receiver need not use the same names internally, but it must reject exactly the listed cases, and a harness should map its own errors onto these.

| Error | Meaning |
| --- | --- |
| `truncated` | Shorter than the fields it must hold: a packet under 18 bytes, a body shorter than its type lists, a carried radio packet under 18 bytes, a cut-off entry or field |
| `tooLong` | Longer than the size limit in force (`maxLength`), a carried radio packet over 255 bytes, or a USB frame longer than a 1,024-byte packet can encode to or decoding to more than 1,024 bytes |
| `badVersion` | Header version not 1 (pairing data: format version not 1) |
| `wrongDirection` | Direction bit is not the one the receiver expects, or, after the tag verifies, the message type does not match the direction: types 0x80 and above come from the hub, lower types go to the hub (section 5) |
| `badAddress` | Address 0 or 0xFFFFFFFF |
| `badCounter` | Counter 0 |
| `badTag` | The 8-byte tag does not verify |
| `unknownType` | Message or setup type not in version 1; the file also gives `messageType`, the byte found |
| `badLength` | A length byte above its field's limit (log text 64, Wi-Fi name 32, Wi-Fi password 64) |
| `badValue` | A byte outside its allowed values: a setup message not starting with 0xF1, or a setup boolean other than 0 or 1 |
| `badFrame` | Not valid COBS |
| `counterExhausted` | No sending counter left (section 4) |

Each rejected case breaks exactly one rule, so the order in which a receiver applies its checks cannot change the expected error, apart from the two orderings the spec fixes (section 3): nothing encrypted is checked before the tag, and a length byte over its limit is `badLength` even when the data after it is also cut short.

Counter rejections use a separate pair: `duplicate` (already accepted, or equal to the last accepted) and `tooOld` (below the window, or below the last accepted).

Every file has `schemaVersion` (1 for the layout described here) and `protocolVersion` (1).

## Message files

One file per message type, named after it: `heartbeat.json`, `door-changed.json`, `cover-changed.json`, `button.json`, `started.json`, `update-query.json`, `update-status.json`, `siren-report.json`, `hello.json`, `forwarded-packet.json`, `gateway-status.json`, `transmit-result.json`, `interference.json`, `log-entries.json`, `reply.json`, `disarmed-notice.json`, `update-offer.json`, `key-change.json`, `siren-command.json`, `siren-settings.json`, `welcome.json`, `transmit-request.json`, `gateway-settings.json`.

Top level: `messageType` (the type byte), `name`, `direction` (of every case in the file), `cases`.

Each case:

| Field | Type | Meaning |
| --- | --- | --- |
| `name` | text | What the case shows |
| `canonical` | boolean | `true`: encoding `fields` must give exactly `plaintext`, and sealing must give exactly `packet`. `false`: decode only; the packet is one a receiver must accept but an encoder never writes (header low bits set, extra bytes after the body, or log text that is not valid UTF-8). It must still open and decode to `fields` |
| `key` | bytes (16) | The device's key |
| `direction` | number | 0 or 1 |
| `address` | integer | Device address |
| `counter` | integer | Sender's counter |
| `binding` | bytes (0, 4, 8 or 16) | The binding of section 4, empty when none applies |
| `maxLength` | integer | Size limit to open with: 255 (radio) or 1,024 (WebSocket and USB) |
| `messageType` | integer | Same as the file's |
| `fields` | object | The body, field by field, as below |
| `plaintext` | bytes | Type byte followed by the body: what is encrypted |
| `nonce` | bytes (13) | Address (4, LE) · direction byte · counter (4, LE) · four zero bytes |
| `associatedData` | bytes | The packet's first 9 bytes followed by `binding` |
| `packet` | bytes | The complete packet: 9 clear bytes, encrypted plaintext, 8-byte tag |

To check a decoder: open `packet` with `key`, `direction` as the expected direction, `binding` and `maxLength`; it must succeed with this `address`, `counter` and `messageType`, and decode to `fields`. To check an encoder (canonical cases only): encode `fields` and compare with `plaintext`, then seal and compare with `packet`. `nonce` and `associatedData` are there to locate a mismatch.

### Fields

Listed in wire order. `u8`, `u16`, `u32` are unsigned, `i8`, `i16` signed, all little-endian. `bytes(n)` is a fixed-length byte string, `rest` a byte string running to the end of the body. `flags` is an object of booleans, one per named bit, bit 0 first; other bits are written as 0 and ignored when read. `version` is an object `{ major, minor, patch }`, three `u8`. Values with a unit conversion hold the raw wire value; the name says the unit.

| Welcome (0xA0) | `hubRandom` bytes(8) |
| Transmit request (0xA1) | `when` u8, `gatewayTimeMicros` u32, `dataRate` u8, `powerDbm` i8, `priority` u8, `packet` rest (18 to 255 bytes) |
| Gateway settings (0xA2) | `settingsVersion` u8, `siteChannel` u8, `listenDataRateMask` u8, `statusIntervalSeconds` u8, `interferenceThresholdDb` u8, `interferenceSeconds` u8, `defaultTxPowerDbm` i8, `sirenTxPowerDbm` i8 |

A packet carried inside another (`packet` in forwarded packet and transmit request) is a radio packet of 18 to 255 bytes; shorter is `truncated`, longer `tooLong`. Every carried packet is the `packet` of another case, which its name points to (a heartbeat, the LoRa siren report, a reply, a siren command), except the 255-byte one in `forwarded-packet.json`, which is sealed by the sensor key with a valid clear header but is not itself a case.

## rejected-packets.json

`packets`: packets that must fail to open. Each has `name`, `key`, `expectedDirection`, `binding`, `maxLength`, `packet` (as for valid cases) and `error`, plus `messageType` when `error` is `unknownType`. Open `packet` with the given values; it must fail with `error`. Cases include altered tags, bytes and header fields, a wrong key, a wrong or missing binding, a binding from an old gateway connection, both wrong directions, truncation, the radio size limit, bad version, address and counter values, carried packets of 17 and 256 bytes in forwarded packets and transmit requests, authenticated packets whose type does not match their direction, authenticated packets whose plaintext is not a valid message, and a reply and siren settings with their shorter bodies from before D115.

`replayed`: packets that open, then must be refused by the receiver's counter rule. Fields as above (all open with an empty binding), plus:

| Field | Meaning |
| --- | --- |
| `rule` | `replayWindow` (the hub's rule for sensors and sirens) or `strictlyHigher` (sirens, and both ends of a gateway connection) |
| `stateBefore` | For `replayWindow`, the window as 12 bytes (see below). For `strictlyHigher`, the last accepted counter, an integer |
| `rejection` | `duplicate` or `tooOld` |

## counters.json

Pure counter logic, no packets.

**Window state bytes.** The hub's receive window is stored as 12 bytes: the highest accepted counter (u32 LE), then a 64-bit mask (u64 LE) in which bit *i* set means counter *highest − 1 − i* was accepted. The empty window is all zeros.

- `take`: one step of the sender's rule. Input `step` (64 or 1,024), `next` (the counter about to be used) and `resumePoint` (the value in flash). Output `counter`, `saveResumePoint` (the value to write to flash before sending, or `null`), `nextAfter` and `resumePointAfter`; or `error: "counterExhausted"` when the sender must refuse. A counter that is a multiple of the step makes the sender save counter + step first; a resume point that would exceed 2³² − 1 is refused.
- `powerLoss`: sequences from pairing, where `next` is 1 and the stored resume point is `initialResumePoint` (the step). Each event is either `{ event: "send", count, firstCounter, lastCounter, savedResumePoints }`, meaning `count` packets were sent with counters `firstCounter` to `lastCounter` and those resume points were saved in that order, or `{ event: "powerLoss", resumeFrom }`, meaning sending continues from the stored resume point.
- `restore`: the hub's counter after restoring a backup with `backedUpResumePoint`: `next` is that value plus 2²⁴, or `error: "counterExhausted"` when that passes 2³² − 1.
- `replayWindow`: sequences starting from the empty window. Each step gives `counter`, `accepted`, and either `highest` and `state` (window bytes after accepting) or `rejection`.
- `strictlyHigher`: sequences starting from 0: siren commands, and both ends of one gateway connection (the rule starts again from 0 on every new connection, while the sender's counter carries on). Each step gives `lastAccepted` (before the step), `counter`, `accepted`, and `rejection` when not accepted.

## cobs.json

USB framing (section 10): COBS, then one zero byte.

- `valid`: `data`, its COBS `encoded` form (no zero bytes, no delimiter) and the `frame` as sent (`encoded` followed by `00`). Encoders must produce exactly `encoded`: there is no empty block after a final run of exactly 254 non-zero bytes. Decoders accept the frame with or without that empty block.
- `invalid`: `encoded` bytes (one frame without its delimiter) that must fail with `badFrame`.
- `streams`: a serial stream in `chunks`, fed to a frame decoder in order. `frames` lists, in order, one entry per frame the zero bytes complete: `{ data }` for a good frame, `{ error }` for a bad one. Empty frames, meaning two delimiters with nothing between them, are skipped and produce nothing. A frame that decodes to no bytes at all (`01 00`) is not empty: it is passed on as `{ data: "" }` like any other, and fails later as too short. In addition, a bad frame costs only itself, and a frame longer than a 1,024-byte packet can encode to (1,029 bytes) is dropped as `tooLong`. A frame that decodes to more than 1,024 bytes is also `tooLong`.

## setup-messages.json

Clear-text USB setup messages (section 10).

- `valid`: `setupType` (the second byte), `canonical`, `fields`, `bytes` (the message, starting with `f1`) and `frame` (as sent over USB). `canonical` is as for message cases: when `false`, `bytes` has extra bytes after the fields, which decoding ignores, so the case is decode only. Fields by type: identify (0x01) and erase (0x05) none; identity (0x02) `role` u8, `chipId` bytes(6), `firmwareVersion` version, `paired` boolean (one byte, 0 or 1), `hubIdentity` bytes(8), `developmentBuild` boolean; provision (0x03) `pairing`, pairing data as in the next file; provision result (0x04) `result` u8; set role (0x06) `role` u8. Which builds accept a set role is firmware behaviour; the codec only decodes it, and an unlisted role passes through.
- `invalid`: `bytes` and the `error` they must give.

## pairing-data.json

Pairing data (section 9): format version 1 (one byte, not in `fields`), then `address` u32, `key` bytes(16), `hubIdentity` bytes(8), `firmwareSigningKey` bytes(64), `siteChannel` u8, `allowedDataRateMask` u8, `wifiName` (length u8, then at most 32 bytes), `wifiPassword` (length u8, then at most 64 bytes). The Wi-Fi name and password are bytes, shown as hex, used exactly as sent and never checked as text; a name the user types is encoded as UTF-8. Bytes after the password are ignored. A format version other than 1 is `badVersion`, an address of 0 or 0xFFFFFFFF `badAddress`. Decoders do not check `hubIdentity` against the key.

- `valid`: `canonical`, `fields` and their `bytes`. When `canonical` is `false`, `bytes` has extra bytes after the Wi-Fi password, which decoding ignores, so the case is decode only.
- `signingPrivateKey` (top level): the P-256 private scalar, 32 bytes big-endian, from which every case's `firmwareSigningKey` is derived. It is RFC 6979 appendix A.2.5's test key, kept for later firmware-signature tests. Every case's `hubIdentity` is computed from that key, except the one named "does not match".
- `hubIdentity`: a `firmwareSigningKey` (64 bytes: X then Y, 32 bytes each, big-endian, no leading 0x04) and its `hubIdentity`, the first 8 bytes of SHA-256 over those 64 bytes.
- `invalid`: `bytes` and the `error` they must give.

## units.json

Unit conversions, so every implementation rounds the same way. Encoding rounds to the nearest whole number with an exact half rounded up, toward positive infinity, so −1.5 becomes −1 (section 3, "Rounding"), then applies the field's limits; `null` means the value cannot be encoded (an implementation refuses it).

| Array | Each case |
| --- | --- |
| `batteryEncode` | `millivolts` → battery `byte`: (mV − 2,500) ÷ 10, rounded, then limited to 0–255 |
| `batteryDecode` | `byte` → `millivolts`: 2,500 + 10 × byte |
| `fifteenSecondDecode` | `units` → `seconds`: units × 15 |
| `fifteenSecondEncode` | `seconds` → `units`, or `null` when not a whole number of units from 0 to 255 |
| `tenthsDecode` | `tenths` → `milliseconds`: tenths × 100 |
| `tenthsEncode` | `milliseconds` → `tenths`, rounded, or `null` above 65,535 |
| `clockCorrectionDecode` | `units` → `ppm`: units × 10 |
| `clockCorrectionEncode` | `ppm` → `units`: ppm ÷ 10, rounded, or `null` outside −32,768 to 32,767 |
| `snrDecode` | `quarterDecibels` → `decibels`: quarters ÷ 4 (exact in binary) |
| `airtimeDecode` | `hundredthsOfPercent` → `percent`: hundredths ÷ 100 (compare within 1e-9) |

## time-on-air.json

`cases`: LoRa time on air (section 2) for every data rate and a range of packet lengths, including every length in section 2's table (the 32-byte reply and the 50-byte longest log entry among them). Each case: `dataRate`, `spreadingFactor`, `length` (bytes), `microseconds` (exact integer) and `milliseconds` (the same value as a decimal). Settings: 125 kHz, coding rate 4/5, 8-symbol preamble, explicit header, CRC on, low data rate optimisation at SF11 and SF12. With these settings the time is always a whole number of microseconds, so compare `microseconds` exactly.

`eventListen`: the event listen time (section 8 †), how long a sensor listens for the hub's answer after a door, cover, button or started report, by the data rate the report was sent at. Each entry: `dataRate`, `spreadingFactor` and `milliseconds`. The hub times its event replies from the same table, so both sides test against this one list.

## The firmware update vectors (M3)

From [m3-updates-design.md](../../../docs/m3-updates-design.md) sections 3, 5 and 7, frozen by the joint step 0. The four update messages above are ordinary message files. The C++ codec passes these four files as well:

### started-update.json

Started (0x05) with the two fields M3 adds at the end of its body: offset 8, image flags (bit 0 on trial, bit 1 rolled back since the last confirmed image; other bits ignored); offset 9, the failed version (3 bytes, zeros for none). A receiver that knows them reads them when the body is 12 bytes or more; an 8-byte body is a Started from a device older than M3 and has none (`image` is `null`); a body of 9 to 11 bytes is `truncated`. The library's `decodeMessage` keeps reading Started's 8-byte version-1 body and ignores what follows, as every older receiver does; `decodeStartedImage` reads the new fields, and `openPacket` returns them as `startedImage`. They are kept apart from `started.json`, whose cases stay version 1.

`valid`: sealed packets, with the fields of a message file's case (`name`, `key`, `direction`, `address`, `counter`, `binding`, `maxLength`, `messageType`, `plaintext`, `nonce`, `associatedData`, `packet`; all canonical), and `fields` the version-1 body's fields as in `started.json`, plus `image`: `{flags: {onTrial, rolledBack}, failedVersion}` or `null`. `invalid`: `name`, `plaintext` (type byte and body) and `error`.

### transfer-frames.json

Transfer frames: not packets, in the clear, one per WebSocket message, COBS frame or Bluetooth write or notification. Byte 0 is `prefix` (0xF2), byte 1 the kind, then the body, little-endian:

| Kind | Name | Fields |
| --- | --- | --- |
| 0x01 | Get | `imageId` bytes(8), `offset` u32, `length` u16 (1 to 1,000; else `badValue`) |
| 0x02 | Data | `imageId` bytes(8), `offset` u32, `crc32` u32, `data` rest (1 to 1,000 bytes; none is `truncated`, more `tooLong`) |
| 0x03 | Gone | `imageId` bytes(8), `reason` u8 (0 not available, 1 not granted, 2 paused, 3 out of range) |
| 0x10 | Hello | `address` u32, `deviceRandom` bytes(8), `imageId` bytes(8), `bytesHeld` u32, `largestData` u16 |
| 0x11 | Open | `tag` bytes(16) |
| 0x12 | Done | `imageId` bytes(8), `result` u8 (0 verified, 1 refused), `reason` u8 (as update status) |

Offsets count from the first byte of the 128-byte image header. Bytes after a fixed frame's fields are ignored. A first byte other than 0xF2 is `badValue`, an unknown kind `unknownType` with `messageType` the kind byte.

`crc32`: `name`, `data`, `crc32` (an integer): CRC-32 with the reflected polynomial 0xEDB88320, initial value and final XOR 0xFFFFFFFF; "123456789" gives 0xCBF43926. `valid`: `name`, `canonical`, `kind`, `fields` (without the kind), `bytes`, and for Data `intact` (whether `crc32` matches the data). Canonical frames encode exactly to `bytes`, the encoder computing a Data frame's CRC; decode-only ones carry extra bytes after the fields, or a Data frame whose CRC does not match (read, then dropped by the receiver). `invalid`: `name`, `bytes`, `error`, plus `messageType` for `unknownType`.

### image-header.json

The 128-byte header the hub signs for every image (section 3). Bytes 0 to 63: `HSNI`, format 1, flags (bit 0 an owner's own build), roles (bit 1 sensor, bit 2 siren, bit 3 gateway: the bit is `1 << role`), target (1), version (3), a zero byte, image bytes u32, the image's SHA-256 (32), the signing hub's identity (8: the first 8 bytes of SHA-256 of its 64-byte signing key, §9), 8 zero bytes. Bytes 64 to 127: ECDSA P-256 over SHA-256 of `label` (`hsn-image/1`), a zero byte and bytes 0 to 63; `r` then `s`, 32 bytes each, big-endian. The image id is bytes 16 to 23. Unused flag and role bits are ignored.

`signing` records how the vectors were signed: RFC 6979 deterministic, the message hashed once with SHA-256, `s` not normalised to the lower half (`lowS: false`), so a signature can be reproduced exactly; a verifier accepts either half. `signingPrivateKey` is RFC 6979 A.2.5's test key (as in `pairing-data.json`), `signingKey` its 64-byte public key and `hubIdentity` its identity. `rfc6979Sample` is that RFC's own signature of "sample" (`message` as hex, `r`, `s`), to pin the primitive. `image` is the test image every valid header's hash names.

`valid`: `name`, `fields` (`flags` {`ownBuild`}, `roles`, `target`, `version`, `imageBytes`, `imageSha256`, `hubIdentity`), `signedBytes` (label, zero byte, bytes 0 to 63), `signedSha256`, `signature`, `header` (all 128 bytes) and `imageId`. Signing `fields` with `signingPrivateKey` must give exactly `header`.

`checks`: what a device checks before it writes a byte, in order: 1. magic, format, target and the zero bytes, or fewer than 128 bytes (`reason` 6, badHeader); 2. the hub identity (7, wrongHub); 3. its role's bit (8, wrongRole); 4. image bytes within the slot (9, tooLarge); 5. the signature (10, badSignature); 0 when all pass. Each case: `name`, `header`, `expect` {`hubIdentity`, `signingKey`, `role`, `capacity`} and `reason` (an update status reason). Cases that break two rules show which check comes first.

### ble-update-session.json

The update service over Bluetooth (section 5): `serviceUuid`, `rxUuid` (the phone writes, without response) and `txUuid` (the device notifies). Every address below is a u32 written **little-endian**, as everywhere in the device protocol.

`sessionKeys`: `name`, `deviceKey` (16), `nonce` (8), `address`, `info` (`hsn-ble-update/1`, a zero byte, the address) and `sessionKey`: HKDF-SHA256 with the device key as input key material, the nonce as salt and `info`, 32 bytes. `openTags`: `name`, `sessionKey`, `address`, `deviceRandom` (8, from Hello), `imageId` (8) and `tag`: the first 16 bytes of HMAC-SHA256 under the session key over `hsn-ble-open/1`, a zero byte, the address, the device random and the image id. `names`: `address` and `name`, the device's name in its scan response during an update window: `hsn-` and the address as 8 lower-case hex digits, most significant first.

## The app channel's vectors (M2)

`app-*.json` are the app channel's vectors (docs/m2-design.md section 10), owned in step 1 by **A1**, in the formats `packages/protocol/src/app/vector-formats.ts` freezes. The device protocol's vectors above are unchanged by M2.

## The relay's vectors (M4)

`relay-*.json` are the relay's vectors (docs/m4-design.md section 11), owned by **B1**, in the formats `packages/protocol/src/relay/vector-formats.ts` freezes, written by `bun packages/protocol/src/relay/vectors/relay-vectors.ts` and checked independently by `verify/verify-relay-vectors.mjs`. Each file's `description` gives every rule needed to implement from it, in the order a receiver checks:

- `relay-xn.json`: `Noise_XN_25519_ChaChaPoly_SHA256` on a hub's link (`hsn-relay/1`) and a relay's link to the push service (`hsn-relay-peer/1`), and the handshakes that must fail.
- `relay-push.json`: sealed pushes as exact bytes (the `h` format and `PushContent`, with every field's bounds), and `h` strings that must not open, each with its reason. The phone's own code (Swift and Kotlin) tests against this file.
- `relay-frames.json`: the links' text frames, accepted or refused by direction, their binary frames with their bytes or their refusal, and the links' close codes with what the closed side does next (4403, `refused`: stop and report once, never retry on a timer).

### Compact values (`relay-frames.json` only)

A few frames are as large as a link allows (131,072 bytes of text, 65,540 and 262,149 bytes of binary) or one byte larger. So that they do not fill the file with hex, four fields may be written compactly: a text frame's `text`, and a binary frame's `bytes`, `frame.message` and `frame.bytes`. Each is either:

- **the value itself**: a JSON string (text, or lower-case hex as everywhere else); or
- **an array of pieces**, at least one, joined in order into that string. A piece is either a JSON string, taken as it is, or an object `{"repeat": <string>, "times": <n>}`, which stands for `repeat` written `n` times one after another. `repeat` is never empty and `n` is an integer from 1 to 16,777,216; the object has no other fields.

For a hex field every piece, and every `repeat`, is lower-case hex of whole bytes, and the joined string is the bytes' hex. For example `["01ffffffff", {"repeat": "a5", "times": 3}, "02"]` is the bytes `01 ff ff ff ff a5 a5 a5 02`. Expand every field first, then run the case as if the field had been written out in full. The other relay files, and every other file in this folder, write their values in full.
