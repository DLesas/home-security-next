# Architecture and decisions

Last updated 2026-11-18.

## Components

```
Door sensor (battery)  ──┐
                         ├─ 868 MHz LoRa ─→ Gateway(s) ─ Wi-Fi ─┐
Siren controller  ───────┘                                      │
   └──────────────────────── Wi-Fi, second path ────────────────┤
                                                                ↓
                       Hub (user's computer) ← phone app and web app at home
                                 │ outbound connection, end-to-end encrypted
                                 ↓
                       Relay (public server) ← phone app away from home
```

All three devices are the same ESP32-S3 board (D49). At home the phone app and the web app talk to the hub directly. Away from home only the phone app is available, through the relay (D31).

| Component | What it does |
| --- | --- |
| Door sensor | Sleeps, wakes on door, button, cover tamper or timer, sends one LoRa report, sleeps again. |
| Siren controller | Always powered, listens on LoRa and Wi-Fi, switches a separate sounder on and off on the hub's command. |
| Gateway | Forwards LoRa packets to the hub and the hub's replies and commands back. Cannot read them and holds no alarm logic (D71). |
| Hub | Decides everything: armed state, schedules, when the siren sounds, notifications, users, firmware. One TypeScript service with an embedded database. |
| Video worker | Part of the hub install, run as its own process: reads cameras, detects motion and objects, records. Sends only events to the hub. |
| Relay | Carries encrypted traffic between apps and a hub that has no public address. Cannot read it. |
| Apps | Arm and disarm, show state, pair sensors over Bluetooth, update out-of-range sensors over Bluetooth. |

## Decisions

Items marked † were proposed during the discussion and not explicitly confirmed.

| # | Decision | Reason |
| --- | --- | --- |
| D1 | New repo, written fresh; the old repo is the reference | The old device code is being retired and the hub needs authentication and gateway support throughout. |
| D2 | Tested pieces are carried over, not retyped: the portable firmware core and the schedule logic. For the firmware this turned out to mean its behaviour and its tests, rebuilt as scenarios: the old code is a blocking Wi-Fi and HTTP loop and is reshaped or dropped ([firmware-design.md](firmware-design.md), section 9) | They work and have tests or production use. |
| D3 | Firmware in portable C++17 with all hardware behind interfaces | The chip can change without rewriting the logic. |
| D4 | ESP32-S3 with ESP-IDF for sensor, siren and gateway | Wi-Fi, Bluetooth, low sleep current and enough pins on one chip. |
| D5 | 868 MHz LoRa carries all events, heartbeats and siren commands | Range of hundreds of metres to a kilometre at a battery cost Wi-Fi cannot match. Sensors do not depend on Wi-Fi coverage; the gateway still uses the home network to reach the hub (D44, D81). |
| D6 | The existing Raspberry Pi Pico devices are retired, not fixed | Replaced by this design. |
| D7 | Only the hub triggers the siren | One place holds the alarm logic. A dead hub means no siren; the sensor's own buzzer is the backup. |
| D8 | A sleeping sensor learns it is armed at its next heartbeat, up to one interval late | Accepted. The hub still decides the siren correctly; only the sensor's buzzer backup lags. |
| D9 | Sensor silence and cover tamper send a phone notification and do not sound the siren | Avoids false alarms from flat batteries and radio dropouts. |
| D10 | Firmware updates over Wi-Fi when in range, over Bluetooth from the phone otherwise | LoRa is far too slow for firmware images. |
| D11 | Pairing over Bluetooth with a code shown on the unit's own display (D85) | No serial cable or Wi-Fi setup for users. |
| D12 | Remote access through a relay; a default relay is operated for all users, and a hub can be pointed at a self-hosted one | Users create no third-party account and open no router ports. |
| D13 | Users and permissions are in the hub from the start. Each phone is given a person's name when it is linked. While user management is off, every person has every permission and the permission settings are hidden; switching it on reveals them | Simple by default, history says who did what, and turning on user management needs no rework. Amended by D33 (custom permissions, not roles) and D61 (no logins). |
| D14 | Cameras and video are built in this repo, after the core system works | The core system comes first. |
| D15 | The hub is one TypeScript service with an embedded SQLite database; no Redis and no PostgreSQL | Anyone can host it on an ordinary computer. Redis existed to connect TypeScript and Python services, and neither split remains. |
| D16 | The hub ships as a native installer per operating system that registers a background service and opens a setup page in the browser; it is not an Electron app and does not need Docker | Close to one-click setup, and the hub keeps running at boot and with no one logged in. |
| D17 | Everything on the hub is TypeScript, video included; no Python at run time | One language and one install, with no mix of binaries and containers. |
| D18 | The MOG2 and KNN background models are reimplemented in TypeScript and run on the GPU as WebGPU compute shaders | Removes OpenCV and Python, and works on NVIDIA, AMD, Intel and Apple graphics hardware; the old GPU path was NVIDIA-only. |
| D19 | A CPU implementation of the same models exists as a fallback | Not every host has a usable GPU. |
| D20 | Object and face detection run exported ONNX models through ONNX Runtime; PyTorch is used only to prepare models | PyTorch is several gigabytes and was the reason the old system needed Docker. |
| D21 | Video runs in its own process, started and supervised by the hub | A crash or a busy CPU on the video side must not delay the siren. |
| D22 | Arming uses modes over groups: sensors belong to groups, and modes such as Away, Home and Night each arm a chosen set of groups. Single sensors can still be armed by hand | "Armed downstairs while we sleep upstairs" without arming sensors one by one. |
| D23 | Every armed door gives an entry countdown before the siren, unless that sensor's countdown is set to zero (D86). The sensor sends the door event at once and the hub runs the countdown | A sensor smashed during the countdown cannot stop the siren. |
| D24 | During the countdown the sensor buzzes and keeps its radio listening. The hub sends one "disarmed" message through the gateway to stop it, transmitted twice for reliability ([protocol.md](protocol.md)); otherwise the buzzer stops when the countdown ends | Warns the person at the door. One message instead of repeated check-ins, and listening costs battery only during countdowns. |
| D25 | First-version controls: phone app, schedules, and phones leaving or arriving. Presence only offers to arm or disarm; nothing changes without a tap | A flat or lost phone must not change the home's security. No keypad or tag reader yet. |
| D26 | On alarm: a critical phone alert with the Disarm button (D51, D76), the siren stops by itself after a set time, and linked cameras record once cameras exist | No SMS or email to outside contacts, which would need an outside sending service. |
| D27 | First-version devices are the door sensor, the siren and the gateway; the hub and protocol allow new device types later | Window and motion sensors wait. |
| D28 | One hub serves one site with one or more gateways; a report heard by two gateways counts once. The phone app can hold several hubs | Coverage for large properties, and a second home. |
| D29 | The hub installer supports Windows, macOS, Linux and Raspberry Pi | Anyone can host it. |
| D30 | Open source: AGPL-3.0 for all software and CERN-OHL-S for board designs; income comes from selling hardware | Trust for a security product, nobody can build a closed product on it, and the AGPL detection model can be used as is. |
| D31 | Two apps: a phone app for iOS and Android, and a web app served by the hub on the home network for setup and management. No desktop app, and no web app through the relay. Both are built from one codebase (D93) | The web page works on hubs with and without a screen. The phone app is needed for Bluetooth and push. |
| D32 | Push notifications go from the hub through the relay to Apple's and Google's services, with content the relay cannot read | Users need no account or token of their own. |
| D33 | Permissions are custom per user. Per sensor and per camera: *manage* (arm, disarm, settings) and *view history*. Global: *manage users* and *manage system* (add and remove devices, hub settings, modes, schedules). A user can switch to a mode only if they can manage every sensor the switch would arm or disarm. All hidden behind the setting in D13 | Replaces fixed roles. |
| D34 | A phone is linked to the hub by scanning a QR code or typing a code, which exchanges keys; further phones are invited from a linked one | Lets the relay carry traffic it cannot read. |
| D35 | Each hub has its own firmware signing key, and devices trust the key of the hub they are paired with. The key cannot change without pairing every device again, since devices find their hub by its hash ([protocol.md](protocol.md) section 10; D136) | People who build their own firmware can update over the air. A compromised hub can push firmware to its devices; accepted. |
| D36 | The siren accepts the hub's command over LoRa and over Wi-Fi | A dead gateway or jammed radio does not silence it. |
| D37 | An all-in-one Docker image may be offered later; it is never required | The native installer already covers every host. |
| D38 | First milestone: door to siren on the bench. Sensor board to gateway board over LoRa, hub on a Mac applying the countdown, siren board switching; arming from a command-line tool, no apps | Proves the whole chain before any interface work. |
| D39 | No exit countdown | Users arm from outside, or from the "everyone has left" prompt. |
| D40 | Defaults: entry countdown 30 seconds, siren automatic stop 5 minutes; both adjustable, the countdown per sensor (D86). The "door opened" notification carries a Disarm button | 30 seconds is tight when the phone is the only way to disarm. Siren time limits vary by country and are unverified. |
| D41 | A home can have any number of sirens. Each group lists which sirens sound for it, set in the interface; by default all of them sound | Up to the user. |
| D42 | The siren device is a controller that switches a separate sounder, so the sounder can be swapped | The current sounder is expensive and very loud; a cheaper default can be chosen later. |
| D43 | No battery backup is required for the siren controller or the gateway, and neither detects tampering (amended by D49 and D83: the shared board gives both a tamper switch and room for a cell) | A power cut takes the hub down too. A silent siren or gateway is already reported. |
| D44 | The gateway connects over Wi-Fi and is powered from USB; it cannot run on battery because it listens all the time | Simplest board. |
| D45 | A schedule targets modes, groups or single sensors, chosen by the user | Covers "Night at 23:00" and "arm the garage at 20:00". |
| D46 | A door opening while disarmed is logged only | No notification or chime. |
| D47 | Sensors receive the home Wi-Fi details from the phone at pairing, for updates | In-range sensors update themselves. |
| D48 | The phone app is new, in React Native with Expo; the old app is a reference for behaviour only. The same code is exported as the web app (D93) | No screens are carried over. |
| D49 | One board design serves as sensor, gateway and siren controller. The gateway and siren run from USB with no cell fitted; the gateway adds an external antenna, and the siren adds a small board that switches 12 V to the sounder | One board to design, order and stock. Supersedes the battery part of D43: a cell can be fitted as backup but is not needed. |
| D50 | Arming a mode with a door open: the app names the door and asks; on continue, the rest arm now and the open door arms when it closes | Matches the old app's behaviour. |
| D51 | Countdown and alarm notifications carry one button, Disarm. It stops the siren and disarms the whole house (with user management on: every sensor that user may manage, D76), and it works even while the phone is locked. There is no separate Silence button | Predictable when rushing through the door. Someone holding the locked phone when the alert arrives could disarm; accepted. |
| D52 | A sensor is reported silent after 3 missed heartbeats (amended by D107: 3 to 8, chosen per sensor). A siren reports every 30 seconds (D73) and is reported silent after 2 misses | Sirens are critical and on mains power, so frequent reports cost nothing. |
| D53 | The hub writes an encrypted backup of its database (settings, users, device keys, signing key) on a schedule to a folder the user chooses, and can export one on demand. A new hub restores it without re-pairing devices | The database is one file on the hub's disk and dies with it. |
| D54 | Updates are announced and the user approves them. The hub installs the new version beside the running one, switches over with a restart of a few seconds, and switches back if the new version fails to start. It never switches during a countdown or alarm. Device firmware is rolled out the same way through the two slots | Nothing changes a security system unattended, and there is no long outage. |
| D55 | The default relay is free with fair-use limits and needs no account; each hub is identified by its own key. To be reviewed once real running costs are known | Without video the relay carries only small messages and push notifications. |
| D56 | Remote live video goes directly between phone and hub, with the relay only introducing them; the relay carries video at reduced quality where a direct path is impossible | Keeps relay costs small. |
| D57 | History: door events, arming, alarms and warnings are kept 1 year; routine heartbeat readings 30 days; both adjustable | Bounded database size. |
| D58 | Apps are in English with all text in translation files | Languages can be added without code changes. |
| D59 | Nothing readable leaves the home by default. The relay sees only encrypted traffic, its timing and size, the internet addresses of hubs and phones, the phones' push tokens, which release a hub fetches, and, for per-hub names, the hub's home-network addresses (D79). Crash reports are opt-in and carry no personal or security information | Privacy. The relay can still tell that a hub sent a push at a given time; accepted. |
| D60 | No time-limited access for users | Not needed. |
| D61 | No passwords. A browser on the hub computer itself is trusted without sign-in. Every other device is linked by QR code or one-time code and then proves itself with its own key, which the hub ties to a user and that user's permissions. Remote users are added by an expiring invite. A lost device is removed by another user; with no linked device left, a new one is linked at the hub | Nothing to forget, guess or phish, and no recovery mechanism to attack. Extends D34 and replaces "one household login" in D13 with named people. |
| D62 | A hub with no screen prints its first linking code in the installer's terminal. The local page requires a secret only the installing account can read, and the hub defends against web pages that target local addresses | Closes the gaps of trusting the local machine. |
| D63 | The phone app can be locked behind the phone's fingerprint or face check. Actions on notifications do not ask for it | Protects an unlocked phone left lying around without slowing down a disarm. |
| D64 | When the hub goes quiet, the relay alerts the phones that the hub cannot be reached (delay and wording: D96). The installer stops the hub computer from sleeping. No device takes over the hub's alarm logic | Keeps D7 intact and the gateway simple; the user knows about the gap instead of the system hiding it. |
| D65 | No panic button. Each siren has a short test from its settings page | Matches the current app; sirens otherwise sound only from a real alarm. |
| D66 | No data is imported from the old system. The old system guides which features to build where that makes sense | All devices are new and are paired again anyway. |
| D67 | When the siren stops by itself and nobody has disarmed, everything stays armed. The door that set it off is ignored until it closes, then arms again | A door left open cannot sound the siren over and over, and every other door still protects the house. |
| D68 | Disarming by hand while a schedule has the house armed keeps it disarmed until the schedule's next arm or disarm time | The schedule still arms again as usual; no extra rules to remember. |
| D69 | Everyday notifications (arm and disarm, sensor offline, low battery, updates) go to every user for the sensors they can view; each user can turn categories off on their own phone. Countdown and alarm notifications cannot be turned off (who receives them: D75, D76) | Sensible default for a household, quiet for those who want it. |
| D70 | No buildings or rooms. Sensors are organised only by the user's own groups, the same groups used for arming and choosing sirens | One way to organise instead of two. |

Added in the consistency review of 2026-11-11:

| # | Decision | Reason |
| --- | --- | --- |
| D71 | Only the hub answers LoRa packets; gateways only forward. Which packets get an answer is in D72. Traffic between a device and the hub is encrypted end to end with the device's key, so a gateway can neither read nor forge it. The reply to a door event says whether an entry countdown has started, and the sensor starts buzzing on that reply | If the hub is down, sensors get no reply and fall back to their own buzzer (D7). Two gateways cannot both answer one packet (D28). A stolen gateway reveals nothing. Replaces the earlier proposal that gateways answer from a cached copy. |
| D72 | A sensor's heartbeat carries the armed state and settings version it holds. The hub replies only when they differ, to every few heartbeats as a link check, and while a firmware update offer waits for that sensor (D139). Door events, tamper, button reports and siren commands are always acknowledged | Keeps the gateway inside its airtime limit while sensors still learn changes at their next heartbeat (D8). |
| D73 | The siren controller reports every 30 seconds over Wi-Fi, and over LoRa straight away whenever a Wi-Fi report fails. It also sends a LoRa check every few minutes, so a dead backup path is found before it is needed. Losing one path is a warning; losing both counts as silent (D52). Hub commands go out on both paths at once; the siren acts on the first copy and its counter check discards the second (D36, LR2) | Frequent reports cost no LoRa airtime, and both paths are proven to work. |
| D74 | Armed state is held per sensor. Switching to a mode arms exactly that mode's sensors and disarms the rest; arming a group or a single sensor adds to what is armed. A sensor may be in several groups; when it triggers, the sirens of all its groups sound, and a sensor in no group sounds every siren | Gives one clear answer when modes, groups, single sensors and schedules overlap. |
| D75 | Always on, cannot be turned off: countdown, alarm, cover tamper, a device going silent while armed, siren silent, hub offline. Can be turned off per phone: arm and disarm, low battery, updates, a device going silent while disarmed | Refines D69: the warnings that mean the home is not protected stay on. |
| D76 | Countdown and alarm alerts go to every user who can view the triggering sensor. The Disarm button appears for every user who may disarm that sensor; pressing it stops the siren and disarms every sensor that user may manage. With user management off, that is the whole house (D51) | Anyone responsible for that door can stop the alarm, without disarming sensors they have no rights over. |
| D77 | Push notifications always go through the operated push service, also for hubs on a self-hosted relay. A fully self-hosted system needs its own build of the phone app | Apple and Google accept pushes for an app only from that app's publisher. |
| D78 | The backup encryption key is held by every linked phone. A new hub is restored by opening the backup file and linking one of those phones, so there is no backup password | Keeps D61's "no passwords" and still lets a lost hub be rebuilt. |
| D79 | Browsers other than the one on the hub computer reach the web app over HTTPS at a per-hub name under a domain run by the relay operator. The name points to the hub's home-network address and carries a real certificate; traffic stays on the home network. The hub detects a home router that blocks its name and tells the user | On plain HTTP, any device on the home network could alter the web app as it loads and so take over a linked browser. Needed for hubs with no screen (D62). Building it is a one-off; running it needs a yearly domain renewal and a small name service beside the relay. The app's own encryption no longer depends on it ([stack.md](stack.md)). |
| D80 | Sirens keep sounding on their own timer if the hub restarts (SR5). The hub saves countdown deadlines and alarm state as they change. On restart it asks each siren for its state, sounds the sirens for any countdown that ran out while it was down, and does not re-trigger an alarm that is already sounding | A crash during an alarm only needs the hub's state to match the sirens. A crash during a countdown must not cancel the alarm. |
| D81 | A gateway can be connected to the hub computer by USB cable, and then talks to the hub over serial USB only. Without the cable it uses Wi-Fi (D44) | Takes the Wi-Fi router out of the alarm path when the gateway can sit near the hub. The board already has USB. |
| D82 | Each gateway measures the radio noise level between packets. Sustained interference raises an always-on alert, critical while armed; it does not sound the siren | Jamming at the door would otherwise go unnoticed by the hub for about 9 minutes. The sensor's own buzzer still covers the door itself (DS6). |
| D83 | No alarm standard is targeted. EN 50131 grade 2 was researched ([S3](spikes/S3-en50131-grade2.md)) and set aside on 2026-11-12: it would need a dedicated tamper-protected hub box with 12 hours of backup, extra tamper hardware on every device, and behaviour that contradicts D9, D50 and D51. The shared board still gives every device a cover tamper switch and room for a cell | Certification would change what the product is. The report is kept in case this is reopened. Amends D43. |
| D84 | Official hub and firmware releases are signed with the publisher's key and fetched through the relay connection. The hub checks that signature, then signs firmware with its own key for its devices (D35). Owners can still load their own builds | One trusted source, no extra outside connection, and self-builders keep control. Settles O2. |
| D85 | Every board has a small e-paper display. A device creates its own pairing code on first boot and after a factory reset, and shows it as text and a QR code; the image stays without power. It sits under the sliding cover with the button | No label printing and no factory tool, the secret never exists outside the device, and the phone can scan the code. |

| # | Decision | Reason |
| --- | --- | --- |
| D86 | The entry countdown is set per sensor. The house default is 30 seconds; a sensor set to zero sounds the siren at once and does not buzz. Closing the door does not cancel a countdown | Doors nobody should enter through, such as a patio or side door, need no warning time. Amends D23 and D40. |
| D87 | A schedule entry is one action at one time: switch to a mode, or arm or disarm a group or a sensor. It can be recurring or one-time. The old system's arm-and-disarm pairs are not carried over; its timing logic is | A mode has no natural "undo", so "Night at 23:00" and "Home at 07:00" are two entries. Amends D2 and D45. |
| D88 | A sensor's own alarm, used when the hub does not answer (DS6), sounds for about 3 minutes while the sensor keeps trying the hub. It stops early when the hub answers "disarmed" or when the button under the cover is pressed | The owner can quieten it while the hub is down. Anyone at the door can too; accepted, since it is only the small buzzer and the cover tamper is still reported once the hub is back. |
| D89 | A factory-reset hold on an armed sensor is reported and the sensor buzzes. If the hub answers, the reset is refused; if nothing answers through the whole 10 minutes of retries, it goes ahead | A sensor whose hub is lost for good can still be reused, and a live hub always hears about an attempt. Amends DS8. |
| D90 | A new hub has two fixed modes that cannot be edited or deleted: Away arms every sensor, including new and ungrouped ones, and Disarmed arms none. Every other mode is made by the user | The two everyone needs work before any group exists. Refines D22. |
| D91 | An approved firmware update is held for each sensor until that sensor is disarmed, and the app reminds the user when a sensor stays armed. Gateways and sirens update one at a time and never during a countdown or alarm | A sensor cannot report its door while it restarts into the new image: about a second, not the minute first thought (amended by D135). Refines D54. |
| D92 | The countdown notification is a critical alert too, like the alarm notification | An owner who is away hears about a break-in 30 seconds sooner. Coming home with a muted phone makes noise; accepted. Amends D26. |
| D93 | The phone app and the web app are one React Native (Expo) codebase; the web app the hub serves is its web export. Bluetooth, push, presence and the app lock exist only in the phone build. First-time setup and everything else are in both (D105) | Every shared screen is written once. Amends D31 and D48. |
| D94 | The hub runs on Bun. Its three runtime-specific pieces (starting the web server, the SQLite driver, and AES-CCM, which Bun lacks and the hub implements on Bun's AES block cipher) sit behind small interfaces, so a move to Node stays a day's work. Before the hub milestone: Windows, Linux on x64, running as a service at boot, and a week-long run are checked | Spike [S1](spikes/S1-runtime.md): about a third of Node's memory at rest, a smaller install, and every native add-on loads. Settles the runtime half of O7. |
| D95 | A Disarm ends an alarm only when every sensor that set it off is then disarmed; otherwise the sirens run on to their automatic stop (D67). A second door opening during a countdown or an alarm adds the sirens of its groups | Defines the case where a user's Disarm (D76) does not cover every triggering sensor. |
| D96 | The relay alerts the phones after 3 minutes without contact from the hub. The alert says the hub cannot be reached and alerts will not arrive, and a second one says when it is back. It breaks through silent mode only when the phone last saw the home armed, which the phone decides by itself. A hub restarting for an update announces it and no alert is sent, and a restarted relay starts its 3-minute clock afresh | The relay cannot tell a dead hub from a home internet outage, in which the siren still works, and it must not learn whether the home is armed (D59). A short outage at night does not wake a disarmed household. Amends the wording in D64. |
| D97 | When a gateway goes silent the hub sends one notification naming the gateway and the number of sensors that no other gateway hears, and holds back those sensors' own "silent" alerts. It cannot be turned off while any of those sensors is armed (D75) | One fault, one alert, sent within about a minute and naming the cause. |
| D98 | Presence is opt-in per person. The phone works out leaving and arriving by itself and tells the hub only that. When everyone has left, the hub offers Away; on arriving while armed, it offers Disarm | No location leaves the phone (D59). Details D25. |
| D99 | The hub creates the backup key and gives it to each phone when it is linked. Invites work once and expire after 24 hours | Lets a replacement phone receive the key from the hub. Details D78 and D61. |
| D100 | A new or factory-reset gateway plugged into the hub computer by USB is added automatically, with no click and no Bluetooth step, and the app shows that it was added. A board that is not a gateway, or that belongs to another hub, is left alone | Access to the hub computer's USB port is already trusted (D61), and a gateway can neither read nor forge traffic (D71). The first gateway works before any phone is linked. |
| D101 | Devices on Wi-Fi or USB carry exactly the same encrypted packets as LoRa, over one kept-open WebSocket to the hub on Wi-Fi, or the serial line on USB. Devices have no separate web interface. From M3 the same links also carry firmware transfer frames, which are not packets (D137) | One packet format and one counter check on every path, which is what lets the siren drop duplicate commands (D73). The hub listens on two ports on the home network: one for devices, which speak plain WebSocket because every packet is already encrypted and authenticated, and one for apps, which need HTTPS (D79, D105). Amended 2026-11-14: one port for both was promised here first, and a plain and an HTTPS listener cannot share one. |
| D102 | The hub keeps any countdown, alarm or warning notification raised while it cannot reach the relay, and sends it as soon as the link returns. A late notification says when the event happened and that it was delayed | After an internet outage the owner still learns what happened during it, and cannot mistake an old alarm for a new one. |
| D103 | There is one firmware image for all three roles. Each board stores which role it is, set when it is made or over the serial line, and reports it when pairing. The image size is checked against the flash when the first board build exists | One file to sign, store and roll out, and the hub and app always know what kind of device they are adding (D100). The role code is small beside the Wi-Fi, Bluetooth and radio code every role already carries *(estimate)*. |
| D104 | Each site uses one sensor channel, chosen from 868.1, 868.3 and 868.5 MHz, at 25 mW radiated and within 1% airtime per hour. Hub replies and siren commands go out on 869.525 MHz, where 10% airtime is allowed. A device sends on one frequency and listens on the other. A sensor on the slowest setting lengthens its heartbeat to stay inside 1% | The gateway transmits far more than any sensor, and a 1% band would limit it to about ten sensors. One sensor channel per site, because a gateway's single radio hears one channel at a time and the airtime limit is per sub-band, so more channels would add no airtime. The only added step is one retune between sending and listening (S2). Answers O9. |
| D105 | When a router blocks the hub's name, the hub detects it and says so in the phone app and on its local page. It shows how to add a router exception where the router has one, and always offers its direct home address over HTTPS, with a certificate the browser warns about until the user trusts it. The hub keeps that certificate, so trusting it once is enough. The web app uses no service worker. Web traffic is never passed through the relay. First-time setup can also be done in the phone app | Works on every router and with the internet down, and keeps D31. Shown to work in Chrome and Safari (O12). Chrome refuses service workers on such a page. The first visit behind the warning is unverified; accepted. Setup in the phone app covers a hub with no screen on a blocking router. Amends D93 and settles the fallback in O8. |
| D106 | A door report carries how long ago the door opened, and the hub counts the countdown from the opening. A report that arrives after the countdown would have ended sounds the sirens for whatever is left of their automatic-stop time, counted from when the countdown would have ended; one older than that sends the alarm notification only, saying when the door opened.
